## Design Context

### Users

Self-hosters running homelabs on Raspberry Pi, Proxmox, Unraid, or Linux servers. They have multiple devices (NAS, mini-PCs, gaming rigs) and one or more UPSes powering them. They're technical — comfortable with NUT, MAC addresses, SSH — but they don't want their dashboards to feel like another terminal session.

**Primary context:** the user opens wol-nut on a phone or laptop to (a) confirm the UPS is fine after a brief power blip, or (b) wake a specific sleeping device they want to use right now. They aren't staring at it all day. The interface should reward a 10-second visit.

### Brand Personality

Three words: **simple, user-friendly, informative**.

- **Voice:** plain English, no marketing fluff. Domain jargon (MAC, NUT, UPS, OB/OL) is fine — the audience expects it.
- **Tone:** confident in what it does, quiet about what it doesn't.
- **Emotional goal:** reassurance. The user opens the dashboard to confirm their lab is OK; the UI should make that confirmation instant.
- **Voice cue from the codebase:** "Vibes by @aloks98, tokens by Claude" — informal, single-author project. Don't over-formalize the surface copy.

### Aesthetic Direction

- **Mode:** dark is the canonical experience. Light mode is a courtesy — kept because shadcn ships with it, polished enough to be acceptable, not where tuning effort goes.
- **Reference feel:** a working self-hosted control panel with real actions — like Tailscale's admin UI, Pi-hole's dashboard, or Glance. Not a marketing page; not a data-analytics report.
- **Anti-references:** enterprise NMS UIs (Cisco-style chrome, dense color-coded tables). AI-generated futurist tropes (cyan grid lines on pure black, glowing circles, glassmorphism showpieces). Anything that prioritizes looking impressive over being readable.
- **Density:** generous whitespace. One thing focal per card. When in doubt, add space.
- **Color philosophy:**
  - **Neutral:** stock shadcn zinc tokens (already in `app.css`).
  - **Accent: electric cyan** ≈ `hsl(189 94% 55%)` (Tailwind `cyan-400`/`cyan-500`). Used sparingly — primary buttons, focus rings, key brand moments. Distinct from the semantic palette so it never gets confused for a status signal.
  - **Semantic (do not change):** `green-500` = online / healthy, `emerald-500` = charging, `amber-500` = warning / on battery, `destructive` red = destructive action.
- **Typography:** system stack stays. Mono only for technical identifiers; sans everywhere else.
- **Iconography:** stock Lucide. No custom icon system.

### Design Principles

1. **Reward the 10-second visit.** Most opens are quick checks. Every UPS and monitored device's status should be readable without scrolling and without parsing a legend. Generous whitespace; one focal point per card.
2. **Color encodes meaning, not decoration.** Cyan = primary action / focus / brand. Green = online. Emerald = charging. Amber = warning / on battery. Red = destructive. Never use these for ornament; never use other colors for status.
3. **Mono only for things you'd grep.** MAC, IP, `host:port`, raw NUT status codes go in mono. Names, descriptions, labels, copy stay in sans.
4. **Dark first, light is courtesy.** Tune values for dark mode. Light mode should look acceptable but isn't where attention goes.
5. **Accessible by default.** Every interactive element has an accessible name. Form errors are programmatically associated with their inputs (`aria-invalid` + `aria-describedby`). Color is never the only signal — pair with an icon, label, or text. Target WCAG AA.
